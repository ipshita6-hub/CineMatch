01

What it is & why it exists

The project in three lines

Learns taste from 20 million real ratings, recommends movies a person will probably love, and predicts how many stars they would give. Built end-to-end: model, API, database, website, dashboard.

The problem it solves

Old systems combine user and movie with a fixed formula (the inner product). Real taste is not that simple. NeuMF learns the combining rule from data instead.

Why the inner product is not enough

Matrix factorization gives each user and each movie a list of numbers, multiplies them position by position and adds up. That forces one rigid rule: every taste dimension adds up independently. But someone can love action, love animation, and dislike animated action — the inner product literally cannot express that. It can add ingredients but never cook them.

Core argument. The inner product is a fixed, hand-chosen interaction function. NeuMF makes it learnable — a neural network discovers the combination rule from 20 million examples. That change is worth +10.4% NDCG@10 here.

"Matrix factorization models the interaction with a fixed inner product, which cannot capture non-linear preference structure. NeuMF keeps the linear view in its GMF branch, adds an MLP branch that learns an arbitrary interaction function, and fuses them."

02

The NeuMF architecture

Be able to draw this from memory — it is the heart of the viva.

PartWhat it does
EmbeddingA short list of learned numbers summarising a user's taste or a movie's character. The model invents them during training — nobody writes them.
GMF branchMultiplies user × movie position by position. The linear view — this generalises matrix factorization.
MLP branchGlues both vectors end-to-end and passes them through three layers. The non-linear view — learns rules the inner product cannot express.
Separate tablesEach branch owns its embeddings. Sharing them would force both views into one representation — the paper keeps them apart deliberately.
FusionJoins GMF (32) + MLP (16) = 48 numbers, and one final layer turns that into a single score.

The elegant bit: remove the MLP branch and make the last layer an identity, and NeuMF literally becomes matrix factorization. It is a strict generalisation — which is exactly why beating MF is the right test.

Preprocessing — 7 steps, 31 seconds

  1. Validate shapes, types, ranges
  2. Count missing / duplicates / orphans — all zero
  3. Clean: valid ratings 0.5–5.0 only
  4. Drop users & movies with <5 ratings
  5. Re-index IDs to 0…N-1 for embeddings
  6. Build genre, year and TMDB-ID features
  7. Popularity computed from training data only

Leave-one-out split — by time, not at random

Why by time? A real system predicts the future from the past. A random split would let the model peek at later behaviour to explain earlier behaviour — impossible in production, so the score would be dishonest. Why only 80,331 users? A hidden movie only counts as a right answer if the user actually liked it (≥4.0).

Negative sampling — the missing-data problem

MovieLens records only what people did rate; there is no list of dislikes. A model shown only positives would learn to say "yes" to everything. So for every liked movie we draw 4 movies the user never touched and treat them as probably-uninteresting — re-drawn every epoch so nothing is memorised.

Honest caveat, state it yourself: an unrated movie is not a confirmed dislike — the user may never have heard of it. My code and docs call these "sampled unobserved interactions", never "rejections".

How the test is kept fair

  • Each test user gets 100 candidates: 1 real hidden favourite + 99 never-touched movies.
  • That list is generated once with a fixed seed and re-used by all three models.
  • Ties break against the right answer, so a model scoring everything equally gets 0, not a lucky pass.
  • Code asserts no "unseen" movie was actually seen and no movie repeats in a list.

The two metrics

Hit Rate@10 — did we find it?

Is the hidden favourite anywhere in the top 10? Yes = 1, no = 0, averaged over all users. 0.9087 means we found it for 91% of users.

NDCG@10 — how high did we put it?

Rewards placing it nearer the top. Position 1 scores 1.00, position 3 scores 0.50, position 10 scores 0.29, missing scores 0. Harder, and more informative.

Expect this question: "why is popularity already 0.79?" Because the 99 negatives are drawn uniformly from 18,345 movies, so they are mostly obscure long-tail titles that a popular hidden movie easily outranks. That is exactly why I report the baseline — it is the bar NeuMF must clear, and it clears it by 14.79%.

Star-rating prediction — a separate model

A NeuMF score is an unbounded ranking number, not stars. Showing it as stars would be fabrication. So a second model is trained with MSE on real ratings, and its output is squeezed through 0.5 + 4.5 × sigmoid(x) so a prediction is always inside the MovieLens scale by construction, not by clipping.

05

The system that was built

Backend — FastAPI

Model weights load once at startup, then every request is just a lookup and a matrix multiply.

Endpoints: login/register (JWT + bcrypt), recommendations, star prediction, movie search, user ratings & preferences, metrics, health. Unknown user or missing model → popularity fallback, never an error.

Database — PostgreSQL, 7 tables

users · movies (27,278 seeded) · ratings · user_preferences · user_embeddings · recommendation_history · movie_metadata_cache. Managed with Alembic migrations. Dataset user IDs are kept strictly separate from app accounts.

Frontend — React + Vite + Tailwind

Landing, login, onboarding, discover, browse, movie detail, recommendations, profile, and a 6-tab analytics dashboard. Light blush-pink theme. Posters come from TMDB via real IDs; without a key it draws genre placeholders rather than wrong artwork.

Speed — measured, not claimed

Target was under 200 ms. Measured p50 2.73 ms, p95 3.07 ms on uncached requests. Scoring the whole 18,345-movie catalogue for one user takes 0.88 ms, so no shortcuts are needed.

The cold-start trick — your best "extra mile" story

A brand-new account has no trained embedding, so it cannot get NeuMF recommendations. Retraining on 20M ratings for one signup is impossible. The solution is fold-in: after the user rates 3+ movies, we freeze every movie embedding and learn only that one user's vector by gradient descent. It takes about 0.4 seconds and gives genuine NeuMF personalisation with no retraining.

"Below three ratings the API serves the popularity fallback and says so explicitly. At three or more I fit just that user's embedding with all item weights frozen — about 400 milliseconds — so a new account gets real NeuMF results without retraining the model."

06

Likely viva questions

Why NeuMF instead of matrix factorization?
MF scores a pair with a fixed inner product, which cannot represent non-linear taste. NeuMF learns the interaction function instead: GMF keeps the linear part, the MLP learns the rest. Worth +5.04% HR@10 and +10.40% NDCG@10 here.
Why do the two branches not share embeddings?
Sharing would force one representation to serve two different interaction styles and limit the fused model. He et al. keep them separate so each branch learns what suits it.
What is HR@10 and NDCG@10?
HR@10 asks whether the hidden movie appears in the top 10 at all. NDCG@10 also rewards putting it higher — rank 1 scores 1.00, rank 10 about 0.29, a miss scores 0.
Why is your Precision@10 only 0.09? Isn't that bad?
No — there is exactly one relevant item per user, so the best possible Precision@10 is 0.1. Precision@10 is mathematically HR@10 ÷ 10 here. I report it because the PRD asks, and I state the relationship rather than presenting it as independent evidence.
Why 99 negatives? Why not rank the whole catalogue?
99 sampled negatives is the standard He et al. protocol and keeps evaluation affordable over 80,331 users. I acknowledge in my limitations that it is easier than full-catalogue ranking — that is exactly why the popularity baseline already reaches 0.79.
How do you know there is no data leakage?
The split is chronological, popularity statistics come from training data only, training negatives are drawn against training history only, and validation/test rows are never training examples. I also found and fixed a leak in the original notebook, which used one all-data "seen" list for both.
Is the predicted star rating the NeuMF output?
No — and that is deliberate. The NeuMF score is an unbounded ranking logit. Stars come from a separate model trained with MSE whose output is squashed into 0.5–5.0. RMSE 0.9064, beating both the item-mean (0.999) and global-mean (1.083) baselines.
What happens for a brand-new user?
Under 3 ratings: popularity fallback, clearly labelled as not personalised. From 3 ratings: embedding fold-in — their vector is fitted in ~0.4s with all item weights frozen.
Why 20M and not the 25M in the PRD?
20M is the dataset that was supplied and that the original notebook used. Mixing versions would make results incomparable. The deviation is documented in the app, the dashboard and the README.
Did you train on all the data?
Preprocessing, EDA and evaluation use all 19,984,024 interactions. Training used a seeded 5,000,000-positive subsample — a recorded, configurable decision stored in the checkpoint, not a hidden one. One flag switches it to the full set.
How do you know the numbers are real?
Every figure comes from a JSON artifact written by an actual evaluation run, which the API serves and the dashboard displays. Anything never computed shows "Not evaluated" rather than a made-up value. 85 automated tests pass: 19 ML, 44 backend, 22 frontend.

Limitations — raise these yourself, it reads as rigour

  • MovieLens 20M, not the PRD's 25M
  • Trained on 5M of 9.99M positives
  • Sampled-negative evaluation is easier than full-catalogue
  • 99.9% of recommendations still come from popular titles
  • No GMF/MLP pretraining (the paper uses it — likely headroom)
  • Fold-in freezes item vectors; periodic retraining still needed
  • Docker omitted by decision, so deployment is documented not verified
  • Latency measured locally, single process

Closing line if you need one: "The model works, but more importantly the numbers behind it are traceable — every metric on the dashboard comes from an evaluation artifact, all three models were scored on identical candidate sets, and where something was not measured the system says 'Not evaluated' instead of guessing."
